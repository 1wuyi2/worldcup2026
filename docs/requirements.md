## 一、项目概述

本项目按照《互联网数据库开发》课程设计要求，以 2026 年世界杯为主题开发团队门户网站。网站将团队主页与世界杯内容展示整合到一个系统中：一方面展示三位成员、课程成果并展示团队寄语与成员学习心得，另一方面提供世界杯新闻、球队、球员、场馆、赛程和进球信息查询。

系统使用 Yii2 Advanced 框架和 MariaDB/MySQL 数据库，提供公开访问的前台及管理员使用的后台。所有主要业务数据通过数据库管理，前后台操作保持一致。

## 二、建设目标与范围

1. 建立风格统一、导航清晰的世界杯主题网站，具备前台展示与后台信息维护功能。
2. 展示团队简介、三名成员介绍、任务内容和课程成果，提供团队寄语及成员学习心得的公开展示。
3. 发布世界杯新闻，展示国家队、球员、比赛场馆、对阵、比分和进球事件。
4. 管理员可以管理网站主要数据，修改后能在相应前台页面看到效果。
5. 使用 **13 张现行业务数据表**（另保留 1 张历史兼容表），满足课程规定的“数据库表数量超过 10 张”。
6. 使用 Git 与 GitHub 协作，保留每位成员的实际 MVC 开发记录。
7. 提供数据库初始化文件、部署说明、课程文档下载入口，能够在新环境中完成还原和演示。

课程项目以本地部署和验收演示为主，不包含实时赛事直播、账号付费、复杂推荐和大规模并发服务。爬虫、数据自动导入、动态图表和一键部署作为扩展功能，不影响基本系统的交付。

## 三、用户角色

| 角色 | 允许的操作 |
| --- | --- |
| 游客 | 浏览公开网页；查看团队、成员、新闻及世界杯赛事；下载已发布的课程资料 |
| 普通注册用户 | 注册、登录及退出前台；浏览公开内容，不自动获得后台管理权限 |
| 管理员 | 独立登录后台；按实际业务权限维护团队门户、新闻资讯或足球数据 |

公开浏览不要求登录。后台操作须经过身份认证和管理员权限校验；不能将普通注册用户自动视为管理员。前后台共享用户及 RBAC 数据，但登录状态独立。后台访问须具备 `managePortal`、`manageNews`、`manageFootball` 中至少一项权限，各模块仍须单独授权。首次部署使用专门的管理员账号，不在仓库中保存真实密码。

## 六、数据需求

系统使用一个 MariaDB/MySQL 数据库，业务表按三个模块分别命名。现行功能使用 13 张业务表，数据库另保留 1 张历史兼容表；用户、RBAC 和 Migration 等 6 张基础表不计入业务表数量。

| 模块 | 数据内容 | 表数 |
| --- | --- | ---: |
| A：团队门户 | 团队、成员、留言、课程资料 | 4 |
| B：新闻资讯 | 新闻分类、新闻文章、新闻标签、文章标签关联 | 4 |
| C：世界杯赛事 | 国家队、球员、场馆、比赛、进球记录 | 5 |
| **现行业务合计** | | **13** |
| 历史兼容 | `wc_portal_reply` | 1 |
| **业务相关物理表合计** | | **14** |

历史兼容表不计入当前功能需求；公开留言板不提供游客投稿或留言回复。表之间应建立必要的主键、外键和唯一约束；后台录入数据应能直接用于前台展示。表结构、字段和 ER 图以配套《设计文档》为准。

### 数据准备与来源

团队和个人资料由成员自行提供；留言由团队成员提供并由管理员录入；作业资料由小组上传。世界杯新闻根据 FIFA 等公开资料自行整理内容，保存来源名称、链接和发布日期。球队、阵容与比赛结果优先以 FIFA 官方信息核对，可通过 OpenFootball 的公开 JSON 数据辅助录入。

赛事数据按实际可核实范围整理，保持球队、球员、场馆与比赛关联完整。比赛中如存在无法核实的场馆、进球事件等信息，允许暂不展示；模拟数据须明确标注为演示数据。新闻正文应符合来源的使用规则；新闻模块不包含封面上传功能。

项目允许离线 CSV/JSON 导入，网站的正常浏览和后台编辑不依赖自动采集脚本或外部网络接口。

## 七、非功能需求

| 类别 | 要求 |
| --- | --- |
| 安全性 | 后台认证及授权；表单校验；留言安全输出；作业下载路径校验；不提交密码与本地密钥 |

| 可维护性 | 按 Yii2 MVC 分层组织代码；新增 PHP 文件按课程要求添加注释头 |
| 可部署性 | 给出环境要求、数据库初始化 SQL 和部署步骤；支持在新数据库中重建网站 |
| 数据质量 | 实体关联有效，避免重复比赛记录；保留必要来源信息；不将演示数据当作真实记录 |

## 八、项目实施与协作规范

### 8.1 项目开发范围

项目划分为三个业务模块：A 团队门户、B 新闻资讯、C 世界杯赛事。每个模块分别拥有自己的数据表、Model、Controller 和 View。开发分配以模块为单位，避免一人只做页面、一人只做数据库。

**每位成员至少实际编写一份 Model、View、Controller 文件**，并通过 Git 记录对应开发过程。三名成员均参加需求评审、集成测试及最终交付。模块和成员的对应关系在正式任务分配时记录在 GitHub Issues 中，不写入需求基线，以免后续职责调整导致反复修改文档。

### 8.2 团队工具与代码协作

| 工具 | 使用方式 |
| --- | --- |
| Git + GitHub | 代码版本管理，仓库为 `1wuyi2/worldcup2026` |
| GitHub Issues | 记录任务、验收要求、实际负责人和问题处理过程 |
| GitHub Projects | 汇总任务看板，状态为“待办、进行中、待验收、已完成” |
| Pull Request | 合并功能分支、检查文件冲突和完成情况 |

采用 `main` 作为稳定分支、`dev` 作为集成分支，各成员在 `feature/*` 分支开发；公共界面及阶段性集成当前在 `frontend-design` 分支进行；完成模块功能后向 `dev` 提交 Pull Request。公共布局、登录授权、依赖配置和数据库最终导出文件统一集成，避免多位组员同时修改。敏感配置和 `vendor/` 等生成目录不提交仓库。

### 8.3 数据库与代码约定

- 三个业务模块只修改本模块的业务表和相应 MVC 文件，跨模块共享功能先规定接口。
- 每个新增 PHP 文件添加文件功能、作者、日期等注释头；命名风格保持统一。
- 数据库初始化文件为 `data/install.sql`，团队和个人材料分别置于 `data/team/`、`data/personal/`。
- 前台提供团队及个人作业的下载入口，便于验收。
